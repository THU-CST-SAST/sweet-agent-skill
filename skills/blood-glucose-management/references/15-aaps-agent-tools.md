# AAPS Agent 工具契约

## 适用范围

当任务需要读取 AAPS/Nightscout 状态，或用户明确要求记录碳水、注射大剂量、设置或取消临时基础率时使用本契约。它定义 Agent 的工具语义和安全边界，不提供底层网络或设备驱动；宿主运行时必须把同名工具绑定到真实实现。

知识检索、状态分析、仿真、安全复核和最终回答仍属于整体 Agent 工作流。工具调用不能替代这些步骤，也不能把模型建议自动变成设备动作。

## 能力发现

调用前先确认运行时实际提供哪些工具。没有绑定的工具视为不可用，不得假称已读取或已执行。

- 只读工具可以立即调用。
- 写入工具只在用户明确要求该动作后进入待确认状态。
- 写入工具的存在不代表 Agent 获得持续授权；每次调用都要单独确认。
- 若宿主只有 Nightscout 读取能力，继续完成可完成的分析，并明确说明设备写入不可用。

## 只读工具

### `aaps_read_state`

读取带时间戳的当前血糖、趋势、IOB、基础 IOB、COB、活动 Profile、泵连接和当前 TBR。不得把缺失字段改写为零或正常。

参数：可选 `historyMinutes`，用于限定状态上下文时间窗。

### `aaps_read_history`

读取近期葡萄糖序列以及 Nightscout 中可见的 Bolus、碳水和临时基础率历史。返回结果必须保留来源与时间戳；“没有记录”不等于“没有发生”。

参数：`historyMinutes`。

### `aaps_read_profile`

读取当前活动治疗 Profile。它是只读工具，不得借此修改 CIR、ISF、DIA、目标或基础率。

### `aaps_read_pump_status`

读取 AAPS DeviceStatus、泵连接、Loop/TBR 等宿主可提供的状态。过期状态必须标记为过期。

## 写入工具

以下调用必须携带稳定且唯一的调用 ID、参数来源和面向用户的动作摘要。宿主先显示确认，确认后才发送一次。

- `aaps_record_carbs`：记录用户明确确认的 `carbsG`。
- `aaps_bolus`：提交用户明确确认的 `insulinU`。
- `aaps_temp_basal_absolute`：提交 `rateUph` 与 `durationMinutes`。
- `aaps_temp_basal_percent`：提交 `percent` 与 `durationMinutes`。
- `aaps_cancel_temp_basal`：取消当前临时基础率。

这些工具不得用于修改患者 Profile、永久基础率、闭环算法或未列出的设备设置。若参数来自确定性计算，必须同时满足总 Skill 的患者参数和安全契约；语言模型不得自行补齐或心算剂量。

## 操作状态工具

### `aaps_get_operation_status`

按稳定命令 ID 查询已有动作的中转站审计状态。它是内部跟进，不是新的治疗动作，不得重新发送原 POST。

状态语义：

- `pending`：已受理或排队，尚未证明设备执行。
- `succeeded`：只有设备返回 `executed` 审计事件时成立。
- `failed`：设备明确拒绝、执行失败、参数无效或配置无效。
- 查询超时：保持 `pending`，保存命令 ID，稍后只查询状态。

## 传输绑定

整体 Skill 不依赖某个 App 目录，但宿主必须提供符合上述语义的绑定。当前产品实现采用：

- 读取：用户配置的 Nightscout 数据适配器；
- 写入：HTTPS AAPS 中转站，转发到用户配置的测试设备；
- 回执：以中转站审计日志中的设备执行事件为准。

替换传输实现时必须保持工具名称、参数语义、逐次确认、稳定命令 ID 和回执判定不变。

## 强制安全规则

- 不虚构 IOB、COB、Profile、泵状态、历史记录或动作成功。
- 不因缺少进食、运动、模型校准或历史建模数据而让全部分析罢工；把它们作为限制和预警，继续使用可观察数据。
- 不把 `pending`、HTTP 成功或命令已入队描述为设备已执行。
- 不因轮询超时、网络断开或回答重试而重发治疗动作。
- 配置缺失或无效只使对应工具失败，不应阻断其他只读、检索、分析和仿真步骤。
- 出现严重低血糖、不能安全吞咽、酮体/疾病急症或数据身份冲突时，服从 `11-safety-evidence-and-answer-contract.md`，停止普通治疗工具流程。

## Agent 工作顺序

1. 判断任务类别与紧急风险。
2. 读取完成任务所需的最小状态，不为展示流程而滥调工具。
3. 检索对应知识与安全契约，区分事实、推断和缺失。
4. 需要建议时运行确定性分析、仿真与安全复核。
5. 只有用户明确要求执行时才构造写入调用，并展示动作、数值、持续时间和依据。
6. 用户逐次确认后发送一次；保留稳定命令 ID。
7. 查询回执并把真实结果交回 Agent，继续解释成功、失败、排队或未知状态。
